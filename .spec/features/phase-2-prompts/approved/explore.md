# Exploration: MCP Prompts

## Намерение
Реализовать поддержку MCP Prompts (согласно спецификации MCP от 2025-11-25) в генераторе `protoc-gen-mcp`. Prompts — это второй серверный примитив MCP (после Tools), который позволяет определять шаблоны промптов с аргументами на уровне protobuf-сообщений. 

## Исследование
Были изучены ключевые файлы кодовой базы:
- `mcp/options/v1/options.proto` (715 строк): Содержит текущие расширения для сервисов, методов и полей. Следующий свободный номер расширения — 91008. Опции `PromptOptions` необходимо привязать к `google.protobuf.MessageOptions`.
- `internal/codegen/model.go` (47 строк): IR модель в настоящий момент оперирует `FileModel` с `ServiceModel` и `MethodModel`. Для промптов потребуется добавить `Prompts []PromptModel` на уровень `FileModel`, так как промпты будут генерироваться из сообщений (`messages`), а не из методов (`rpc`).
- `internal/codegen/collect.go` (238 строк) и `metadata.go` (456 строк): Архитектура позволяет легко добавить новый `collect_prompt.go` для сканирования `.proto` файла на предмет сообщений с опцией `(mcp.options.v1.prompt)`. Извлечение метаданных (описания, `required` статуса аргументов на базе `optional` флага) аналогично текущей логике для полей.
- `mcpruntime/register.go` (211 строк): Текущая регистрация инструментов использует `server.AddTool()`. Go SDK v1.6.0 предоставляет `server.AddPrompt(prompt *mcp.Prompt, handler PromptHandler)`. Для промптов потребуется аналогичная структура (например, `PromptSpec` и `RegisterProtoPrompt`).

**Особенности MCP Prompts:**
- Аргументы передаются от клиента как плоский `map[string]string`.
- Формат возвращаемого значения — массив `mcp.PromptMessage` (содержащий роли и текстовые/медийные данные).

## Рассмотренные варианты

### Option A: Per-file Prompts Registry (Согласовано с текущей архитектурой)
- **Описание:** Генерация одного интерфейса `<File>PromptHandler` на каждый `.proto` файл. Каждый message с опцией `prompt` становится методом в этом интерфейсе. Добавляется функция `Register<File>Prompts`. В `mcpruntime` добавляется `prompt.go` для парсинга аргументов.
- **Плюсы:** Полностью соответствует текущему подходу для Tools (где генерируется `<File>ToolHandler`). Единообразие для всех 5 языков.
- **Минусы:** Чуть больше boilerplate-кода в генерируемых файлах, если в одном файле много промптов.
- **Сложность:** Средняя.

### Option B: Per-message Prompts Registry
- **Описание:** Генерация отдельной функции `Register<Message>Prompt` для каждого отдельного сообщения.
- **Плюсы:** Максимальная гранулярность регистрации.
- **Минусы:** Нарушает сложившийся в проекте паттерн группировки по файлу (`Register<File>Tools`). Усложняет использование для конечного разработчика (придется вызывать N функций вместо одной).
- **Сложность:** Средняя.

## Рассмотренные варианты: типы аргументов промпта

MCP передает аргументы промпта как плоский `map[string]string]`. Protobuf-сообщения поддерживают числа, булевы значения, вложенные сообщения, массивы и карты. Вопрос: какие типы полей допускать в proto-сообщениях, помеченных `(mcp.options.v1.prompt)`?

### Option C: Только `string` поля (strict)
- **Описание:** Генератор допускает исключительно поля типа `string`. Любой другой скалярный тип (`int32`, `bool`, `double`, `enum`) или составной тип (`message`, `repeated`, `map`) вызывает fail-fast ошибку генерации.
- **Плюсы:** Максимальная простота, нет парсинга строк в рантайме, нет ошибок конвертации, полное соответствие семантике MCP (`map[string]string`).
- **Минусы:** Ограничивает выразительность — если нужно передать число, пользователь вынужден парсить строку вручную в handler'е. Менее идиоматично с точки зрения protobuf.
- **Сложность:** Низкая.

### Option D: Базовые скаляры + парсинг (рекомендуемый)
- **Описание:** Генератор допускает все скалярные типы protobuf (`string`, `int32`, `int64`, `uint32`, `uint64`, `float`, `double`, `bool`, `bytes`, `enum`) в полях промпта. Вложенные сообщения, `repeated`, `map` и `oneof` запрещены (fail-fast). Рантайм-хелпер (`mcpruntime/prompt.go`) конвертирует строковые значения аргументов MCP в нужные типы через `strconv.ParseInt`, `strconv.ParseFloat`, `strconv.ParseBool` и т.д. Перечисления (`enum`) ищутся по строковому имени (`ENUM_VALUE_NAME`).
- **Плюсы:** Идиоматичное использование protobuf (не нужно всё делать `string`). Автоматическая валидация типов на этапе парсинга. Совместимость с MCP-семантикой (строки на проводе → типизированная структура в handler'е).
- **Минусы:** Дополнительная логика парсинга в рантайм-хелперах для Go, Python, Kotlin, Java, TypeScript. Возможны ошибки парсинга (невалидное число/булево значение) — нужна обработка ошибок.
- **Сложность:** Средняя.

## Ограничения и риски
- **Плоская структура аргументов:** Аргументы промпта в протоколе MCP — это `map[string]string`. Вложенные сообщения (`nested messages`), массивы (`repeated`), карты (`map`) и `oneof` в полях промпта запрещены — генератор выдает fail-fast ошибку.
- **Парсинг типов (при выборе Option D):** Рантайм-хелперы конвертируют строки в скалярные типы. Невалидные значения (например, `"abc"` для `int32`) возвращают ошибку `InvalidParams` клиенту.
- **Поддержка в других SDK:** Необходимо убедиться, что Python, Java, Kotlin и TypeScript SDK также поддерживают `AddPrompt`.
- **`bytes` тип:** При `map[string]string` передача бинарных данных возможна только в base64-кодировке. Если допускаем `bytes`, рантайм-хелпер декодирует из base64.

## Рекомендованное направление

**Архитектура регистрации:** Option A (Per-file Prompts Registry) — согласуется с текущим подходом для Tools.

**Типы аргументов:** Option D (базовые скаляры + парсинг) — позволяет использовать protobuf идиоматично. Вложенные типы запрещены (fail-fast).

Итого:
- В `options.proto` добавляется `PromptOptions` как расширение 91008.
- Реализуется `collect_prompt.go` для сбора IR с fail-fast на вложенные типы.
- Добавляется логика рендеринга для 5 языков (генерация `*PromptHandler` интерфейсов).
- В `mcpruntime/prompt.go` добавляется логика парсинга `map[string]string` аргументов в типизированную структуру proto-сообщения.

## Границы scope
- **Must-have (v1):**

- **Needs spike:** 
  - Нет.

## Предположения и открытые вопросы
- `[ASSUMPTION: SDK Support]` Все 5 официальных SDK поддерживают регистрацию промптов на базовом уровне.
- `[ASSUMPTION: Prompt options location]` Расширение `PromptOptions` вешается исключительно на `google.protobuf.MessageOptions` под номером 91008.
- `[ASSUMPTION: Return type]` Обработчик промпта возвращает список сообщений (эквивалент `[]mcp.PromptMessage` в Go), и каждый язык будет использовать свои нативные аналоги этого типа из SDK.
- **Открытый вопрос:** Типы аргументов промпта — Option C (только `string`) или Option D (базовые скаляры + парсинг)? Рекомендуется Option D. См. сравнение выше.
